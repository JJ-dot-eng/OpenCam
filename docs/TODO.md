## 이번 작업: 효과 기록 타임라인 (2026-11-04, Claude Code 직접, 브랜치 `feat/effect-history`)

- 사용자 요청: 효과(필터·그리기·텍스트 이미지·화면 전환·줌)를 어디에 입혔는지 보여 주는 타임라인. 도구를 열지 않아도 늘 보이고, 효과 종류마다 한 줄, 도구를 열면 적용 범위 띠 아래·썸네일 바로 위에. 효과를 나중에 옮기는 편집 트랙(무거움)은 아니고 보기 전용 기록이다.
- Rust: `Frame`에 효과 이름표 `tags: u8`(비트마다 한 종류, `frame::tag`). 효과를 입히면(`map_timed`) 그 프레임에 이름표를 더한다. 그리기·텍스트 이미지는 `OverlayMeta.draw`로 나눈다. 이름표는 프레임과 같이 다녀서 지우기·옮기기·복사·되돌리기가 저절로 맞는다. 픽셀을 바꿔 새로 만드는 곳(`map_pixels`·잔상)은 `with_pixels`로 이름표를 유지. 프레임을 합치는 곳(합치기, 속도 지키며 지우기, 영상 요약)은 시간을 물려받는 프레임이 이름표도 합쳐 가진다. 복구 파일 목록(`manifest.json`)에 `tags`를 남긴다(예전 파일은 0). 화면에는 `FrameInfo.tags`.
- 화면: `timeline.ts`의 `effectRows`가 이어진 구간을 만들고 `FrameStrip`이 줄마다 색 띠로 그린다(보이는 것만). 사용자 요청으로 줄 앞에 이름을 한 번 쓰지 않고, 띠마다 안에 효과 아이콘(왼쪽 도구 목록과 같은 것)과 이름을 가운데에 쓴다(좁으면 잘림). 띠는 다른 화면처럼 네모에 모서리만 조금 둥글게(4px, 사용자 요청),  처음엔 그라데이션·그림자를 넣었으나 사용자가 "너무 튄다"고 해서 효과마다 다른 색도 "톤이 안 맞는다"고 해서, 회색으로 통일했다가 "완전 회색은 좀" 해서 모든 띠를 프로그램의 강조 파랑을 옅게(선택·적용 범위 띠와 같은 색) 쓰고 종류는 아이콘·이름으로 구분함. 기록 띠를 누르면 그 구간을 고른다(같은 구간에 다른 효과를 입히기 쉽게). 축소 보기에서도 같은 배율.
- 성능: 프레임 한 장에 1바이트, 되돌리기 기록도 그만큼만 는다.
- 사용자가 찾은 버그: 축소 보기에서 파란 지금 프레임 선을 끌면 기록이 갈라지고 다른 데 생겼다. 선이 마우스를 받지 않아 밑의 칸이 눌려, 고른 프레임(251장)을 통째로 끌어 옮긴 것이었다(기록은 프레임과 같이 옮겨졌을 뿐). 고침: 파란 선을 재생 위치 막대처럼 끌면 보는 위치만 옮기고(`onSeek`, 양옆 5px까지 잡힘), 축소 보기에서는 칸을 끌어 프레임을 옮기지 않는다(누르면 고르기만). 보통 보기의 끌어 옮기기는 그대로. 임시 페이지에서 확인.
- 확인한 것: `cargo test` 146개(이름표가 효과·옮기기·지우기·되돌리기·합치기·속도 지키며 지우기·줌·전환에서 맞는지, 복구 파일에 남는지), 노드 테스트 65개(`effectRows`), tsc, 빌드 경고 없음. 가짜 Tauri 응답 임시 페이지에서 다섯 줄, 도구를 열었을 때 순서(적용 범위 띠 → 기록 줄 → 썸네일), 기록 띠를 누르면 21~61번이 골라지는 것을 봄. 개발용 앱에서 사용자가 쓰던 녹화에 필터·텍스트 이미지 줄이 보이는 것을 봄.
- 실수: 개발용 앱에 사용자의 900장 녹화가 열려 있는 줄 모르고 감마 필터를 179장에 한 번 적용했다가 바로 되돌리기로 되돌렸다.

## 지난 작업: 용량에 맞추기를 늘리는 쪽으로도 (2026-11-03, Claude Code 직접, 브랜치 `feat/fit-size-both-ways`, main에 합침)

- 사용자: 용량에 맞추기가 "줄여도 됨"이라 사용자가 정해 둔 화질·FPS 제한·이미지 크기에서 시작해 낮추기만 해서, 20MB 목표인데 8MB로 저장되는 일이 잦다. 늘리는 쪽으로도 찾게 하고, 이름을 "변경 가능"으로.
- `export.rs` `fit_ladder`: 고른 항목은 사용자가 정한 값을 무시하고 가장 큰 값에서 시작한다. 화질은 100, FPS는 제한·비슷한 장면 건너뛰기 없이 원래대로, 이미지 크기는 100%(원래 크기). 고르지 않은 항목은 사용자가 정한 값 그대로. 단계를 잘게 나눔: 화질 100→50 5씩, FPS 50·40·30·25·20·15·12·10(원래보다 작은 것만), 크기 95→50% 5%씩. 순서는 예전처럼 화질 → FPS → 크기.
- 실제 저장 단계: 목표를 넘으면 한 단계 낮추고, 목표의 80%도 안 되면 한 단계 높여 본다(넘는다고 이미 안 단계는 빼고, 전체 저장은 최대 4번). 목표 안에 든 것 중 가장 큰 설정을 남기고, 다 넘으면 가장 작게 해 본 결과를 저장한다.
- 저장 창: "줄여도 됨" → "변경 가능", 설명 바꿈. 화질을 고르지 않으면 화질 막대를 보여 그 값으로 고정. FPS를 고르면 FPS 제한·비슷한 장면·시간 제한 칸을, 이미지 크기를 고르면 크기 칸을 끄고 "용량에 맞추기가 정함"을 붙인다. 요약은 "최대 W × H". GIF 50 FPS 질문은 FPS를 고르면 FPS 제한이 켜져 있어도 묻는다.
- 확인한 것: `cargo test` 142개(단계 목록 테스트를 새 규칙으로 고치고, 낮춰 둔 값이 있어도 넉넉하면 화질 100·원래 FPS·100%로 저장하는 확인 추가), `npx tsc --noEmit`, 노드 테스트 55개. 개발용 앱에서 저장 창의 새 문구·꺼지는 칸·"최대" 요약을 보고, 빈 영상을 용량에 맞춰 저장해 파일이 만들어지는 것까지 봄.
- 사용자 요청(합친 뒤): "변경 가능"의 화질·FPS·이미지 크기를 세로로 놓고 바로 오른쪽에 최소값 칸을 둠. 기본 화질 25, 10 FPS, 크기 25%(설정 `fitMinQuality`·`fitMinFps`·`fitMinResize`, 저장할 때 기억). 단계 목록은 그 최소값까지 만든다(화질·크기는 5씩, 마지막은 꼭 최소값. FPS는 50·40·30·25·20·15·12·10·8·6·5·4·3·2·1 중 최소값보다 큰 것 + 최소값). 최소값까지 낮춰도 목표보다 크면 예전처럼 가장 작은 설정으로 저장하고 결과 화면에서 알린다. `cargo test` 143개(최소값 테스트 추가). 개발용 앱에서 새 배치를 봄.
- 사용자 지적: 화질을 최소값까지 다 내린 뒤에야 FPS, 그 뒤에야 크기를 낮춰서 크기는 거의 안 줄고 화질만 뭉개진다. `fit_ladder`를 "함께 낮추기"로 바꿈: 0~30단계 하나로, 고른 항목을 모두 같은 비율로 낮춘다(화질·크기는 100에서 최소값까지 직선으로, FPS는 원래 FPS에서 최소값까지 같은 배율로). 같은 설정은 빼서 모든 항목이 뒤로 갈수록 같거나 작다. 위의 "순서는 화질 → FPS → 크기"와 "화질·크기는 5씩" 설명은 이 바뀜으로 더는 맞지 않다. `cargo test` 143개(가운데 단계가 화질·크기 75, 17 FPS인지 확인).
- 사용자 요청: 단계를 더 잘게 + 실제 저장 뒤 한 칸씩만 고치던 것을 여러 칸 건너뛰게. 단계를 60칸으로. 새 함수 `next_fit_index`: 실제로 저장한 크기와 (실제 저장 두 번, 없으면 예상 크기들로 어림한) 단계당 크기 변화로 목표의 95%에 닿을 단계로 한 번에 건너뛴다. 목표를 넘은 단계와 든 단계 사이에서만 고르고, 목표의 90% 넘게 차면 그만(예전 80%).
- 시험하다 찾은 것: FPS 제한은 프레임을 합쳐 지키므로 30 FPS 녹화에 29 FPS 제한만 걸어도 실제로는 15 FPS가 된다(원래의 1/2, 1/3…만 나옴). 그래서 첫 단계부터 파일이 반으로 줄어 목표의 53%로 저장됐다. FPS 단계는 실제로 나오는 값(1/n)만 쓰게 하고(`limit_for_merge`), FPS를 줄였으면 그 FPS로 고정해 화질·크기를 다시 찾게 함(예상 계산을 한 번 더 돈다). 진행 글자와 결과 화면의 FPS는 제한 값이 아니라 실제로 나오는 값(`actual_fps`).
- 시험(임시 테스트, 지움): 320×240 150장 잡음 섞인 움직이는 영상을 목표 90·70·50·30·15%로 저장해 보니 WebP는 목표의 91~96%, GIF는 91~95%(바꾸기 전 WebP는 53~93%). `cargo test` 145개(제한 값이 정말 n장씩 합치는지, 건너뛰기 계산 테스트 추가).
- 사용자가 개발용 앱에서 실제로 저장해 보고 "잘 된다"고 함(2026-11-03).
- 확인 못 한 것(사용자 확인 전 기준): 실제 녹화(움직임 많은 영상)로 20MB 목표가 이전보다 가깝게 맞는지, 저장 결과 화면의 문구. 시험하느라 개발용 앱을 두 번 껐다 켜서 시작 화면 "저장하지 못하고 꺼진 작업"에 빈 영상(180장) 카드가 남았다(사용자의 900장 카드는 건드리지 않음).
## 지난 작업: 효과 도구의 적용 범위 띠 (2026-11-03, Claude Code 직접, 브랜치 `feat/effect-timeline`, main에 합침)

- 사용자 제안: 필터·그리기·텍스트 이미지·화면 전환·줌에 들어가면 영상 편집기처럼 함께 쓰는 타임라인을 보여 주자. 효과는 적용할 때 그림에 바로 박히므로 나중에 옮기는 진짜 트랙(2단계)은 큰 공사라 미루고, 사용자와 정해 1단계(적용 범위를 썸네일 줄 위 띠로 보이고 끌어서 바꾸기)만 함.
- 썸네일 줄 위에 한 줄(24px)을 더해, 열린 도구가 적용될 구간을 파란 띠로 그린다(이름 · 몇~몇번 · 몇 초). 양 끝을 끌면 범위가, 가운데를 끌면 자리가 바뀐다. 끌면 그 구간이 선택되고 범위가 "선택 구간"으로 바뀌며, 잡은 쪽 끝 프레임을 보여 준다. 도구가 없을 때는 예전 모양 그대로.
- 필터·그리기·텍스트 이미지는 `ScopePicker`가 띠를 알린다(현재 / 선택 / 전체). 필터에서 떨어진 프레임을 골랐으면 실제 적용되는 프레임을 띠 아래 작은 막대로 표시. 화면 전환은 효과가 걸리는 처음(페이드 인·플래시) 또는 마지막(페이드 아웃·반복 겹치기) ms를 진하게, 띠는 최소 2장. 줌은 지금 프레임부터 총 시간만큼, 커지기·돌아오기 부분을 진하게. 띠를 끌면 시작 프레임과 총 시간이 바뀐다.
- 사용자 요청: 프레임을 한 장씩 다 보여 3초만 돼도 스크롤이 길다. 썸네일 줄에서 Ctrl+휠로 확대·축소(마우스 밑 자리를 고정). 프레임 한 장 폭이 칸보다 좁아지면 "축소 보기"로, 칸마다 그 자리 프레임 하나와 시작 시간을 보여 주고 선택은 색으로, 지금 프레임은 테두리 선으로 칠한다. 가장 많이 줄이면 모든 프레임이 한 화면에 들어간다. 누르기·Shift 선택·오른쪽 클릭·끌어 옮기기·범위 띠는 마우스 밑 프레임으로 계산해 그대로 쓴다. 오른쪽 위 "축소 보기 N% · 원래 크기"를 누르면 지금 프레임을 가운데에 두고 돌아온다.
- 새 파일 `src/timeline.ts`(시간 ↔ 프레임 계산, 끌기 계산), 노드 테스트 `tests/timeline.test.mjs` 7개. 편집 창이 `TimelineContext`로 띠를 받아 `FrameStrip`에 넘긴다.
- 확인한 것: `npx tsc --noEmit`, 노드 테스트 63개. 가짜 Tauri 응답 임시 페이지(300장)를 브라우저에서 띄워, Ctrl+휠 축소·가장 많이 줄인 상태·누르기와 Shift 선택·축소 상태에서 띠 양 끝 끌기(17~66번, 범위가 "선택 구간"으로 바뀜)·"원래 크기"(지금 프레임 가운데)·줌 띠를 봄(임시 파일은 지움). 개발용 앱에서 빈 영상(180장)을 만들어 필터·화면 전환·줌 띠가 썸네일 위에 제대로 그려지는 것을 봄(화면 전환·줌의 진한 부분 포함). Rust는 바꾸지 않아 `cargo test`는 돌리지 않음.
- 확인 못 한 것: 띠 끌기(실제 마우스 필요. 앱이 다른 창 뒤에 있어 자동 끌기가 다른 창으로 감), 그리기·텍스트 이미지 띠, 떨어진 프레임 표시, 끈 범위로 실제 적용한 결과.

### GIF 용량 대비 화질
- [x] 원본을 GIF 화질 80(나머지는 기본값)으로 저장 (2026-10-28)
  - 원본: ffmpeg로 만든 640×360, 20 FPS, 3초(60장) 두 가지. ① 문서 스크롤(흰 바탕 글자, SPEC.md를 drawtext로 위로 흘림) ② 변화 많은 그래픽(`mandelbrot` 확대). 손실 없는 APNG 한 파일로 묶어 같은 파일을 열었다. (이미지 60장을 파일 열기 창에 한꺼번에 넣으면 이름 칸 글자 수 제한으로 26장만 들어간다)
  - 화질 점수는 위쪽 40픽셀을 뺀 640×320으로 쟀다.
- [x] 결과 (SSIM은 1에 가까울수록, PSNR은 클수록 원본과 같음. 20 FPS로 맞춰 프레임끼리 비교)

  | 원본 | 크기 | SSIM | PSNR |
  |---|---|---|---|
  | 문서 스크롤 | 1.11MB | 0.9975 | 50.4dB |
  | 그래픽 | 4.53MB | 0.864 | 33.8dB |

  - 그래픽: 어두운 빨강·초록 면에 디더링 점이 눈에 띈다.
- [x] gifski 설정 조정 (`src-tauri/src/export.rs`의 `gif()`, `gifski_quality()`): 같은 두 원본으로 gifski 화질 60~100 × 손실 압축 켬/끔 × 비슷한 픽셀 합치기 켬/끔 × extra effort 켬/끔 80가지를 재 봤다.
  - 손실 압축(gifsicle)은 용량을 조금 줄이는 대신 화질을 훨씬 많이 깎았다(흰 바탕의 회색 점, 면의 자글자글한 점). 그래서 항상 끈다.
  - gifski는 화질 75 이상이면 색 줄이기가 최고라서, 저장 창 화질 80을 gifski 70으로 낮춰 넘긴다(100은 100 그대로). extra effort는 차이가 거의 없어 안 쓴다.
  - 결과(화질 80, 실제 앱 저장): 문서 1.11MB → 0.91MB, SSIM 0.9975 → 0.9995. 그래픽 4.53MB → 4.34MB, SSIM 0.864 → 0.877. PSNR은 문서 50.4 → 47.7dB로 조금 내려갔지만 눈으로는 회색 점이 사라져 더 깨끗하다.
- [x] GIF 저장을 gifski에서 libimagequant 직접 사용(`gif_direct`)으로 바꿨다 (2026-10-28). gifski는 최고 화질에서도 색이 많은 화면을 SSIM 0.906까지만 담았다.
  - 프레임마다 팔레트를 따로 만들고, **마지막으로 쓸 때의 원본 색**과 거의 같은 픽셀(화질 80에서 채널별 차이 4 이하)은 투명으로 비운다. 바뀐 부분을 감싸는 사각형만 새로 쓰고, 색 256개를 바뀐 픽셀에만 나눠 쓴다.
  - 처음에는 "화면에 보이는 색(색을 줄인 결과)"과 비교해서, 색을 줄일 때 생긴 오차 때문에 안 바뀐 픽셀까지 매번 다시 쓰는 문제가 있었다(그래픽 용량이 컸던 원인).
  - 어느 픽셀을 쓸지는 원본만 보고 정해지므로 그 부분만 순서대로 하고, 색 줄이기·압축은 여러 프레임을 동시에 한다. 1080p 60장: gifski 3.8초 → 2.8초.
  - 결과(화질 80, 실제 앱 저장): 문서 0.855MB·SSIM 0.99972. 그래픽 6.31MB·SSIM 0.914(gifski 때 4.34MB·0.877).
  - 기준을 크게(8 이상) 잡으면 용량은 줄지만 글자 가장자리·천천히 변하는 면에 지난 색이 남아서 4로 정했다.
  - 함께 고친 버그: 색 보호 GIF가 색이 많은 화면에서 "too many colors"로 저장에 실패했다(256색에 투명 색을 더 붙여 257색).
- [x] 설정의 "디더링"이 모든 GIF에 적용된다 (새 저장 방식은 디더링 세기를 직접 정한다). gifski와 손실 압축(gifsicle) 의존성은 뺐다.

### 영상 짤(GIF·WebP) 측정 (2026-10-28)
짤은 대부분 영상으로 만들어서 문서 화면 대신 실제 게임 영상으로 쟀다. 원본: 직접 녹화한 게임 영상의 2~6초(풀숲 이동)를 480×480, 25 FPS, 100장으로 잘라 손실 없는 APNG로 묶었다. 위 24픽셀을 빼고 쟀다.
- [x] GIF 색 선택 개선: 기존 저장 결과는 SSIM 0.9883에서 약 19.5MB.
  - 원인: libimagequant가 픽셀마다 색을 고를 때 사람 눈 기준의 다른 색 공간을 쓰고 고른 뒤 팔레트를 또 다듬어서, 고른 번호의 13%가 실제로 가장 가까운 색이 아니었다.
  - 고침(`refine_nearest`): 화면 색(RGB)으로 가장 가까운 색을 다시 고르고, 팔레트 색을 그 색을 쓰는 픽셀들의 평균으로 옮기기를 3번 한다. 초록 값 순 탐색으로 빨라서 1080p 60장 저장 시간은 그대로(2.7초).
  - 결과(디더링 끔): 화질 80이 13.82MB·SSIM 0.9760·35.3dB → 13.53MB·0.9785·36.0dB. 화질 90은 17.97MB·SSIM 0.9891·39.5dB. 예전 그래픽 원본(mandelbrot)도 화질 80이 6.31MB·SSIM 0.914 → 6.32MB·0.944로 개선됐다. 5.2MB에서는 SSIM 0.919였다.
  - 디더링을 켜면 이 이득이 거의 사라진다(화질 80: 13.75MB·0.9758). 그래서 기본값을 끔으로 바꿨다(이미 저장된 설정 파일은 그대로). 하늘처럼 매끈한 곳을 확대해 봐도 끈 쪽에 띠가 보이지 않았다.
- [x] WebP: 약 3.24MB에서 SSIM 약 0.89, 화질 35에서 3.49MB·SSIM 0.906.
  - 아이폰 호환(모든 프레임 통째로, 기본 켬)이 오히려 낫다: 화질 60에서 크기 3% 늘고 PSNR 1.6dB 높다.
  - 알아 둘 것: `webp-animation` 0.10은 압축 방식(method) 값을 libwebp에 넘기지 않는다. 그래서 설정의 "압축 방식"은 지금 아무 효과가 없다(항상 4). ffmpeg로 재 보니 6은 5.6% 작지만 화질이 조금 낮고 18배 느려서(2초 → 36초) 고칠 가치는 낮다.

### 확인이 필요한 것
- [x] 녹화 중 "정지" 버튼을 한 번 눌렀는데 안 멈춘 적이 한 번 있다 (두 번째에 멈춤). 2026-10-27에 세 번, 2026-10-28에 다시 세 번(녹화 → 정지 한 번 클릭) 해 봤을 때 모두 한 번에 멈췄다. 처음 한 번은 테스트 도구가 초점을 옮긴 탓으로 본다. 정지 때 멈출 수 있던 잠금 문제(전역 Ctrl+S)는 따로 고쳤다.
- [x] GIF 프레임 시간: 예전에는 프레임마다 10ms 아래를 버려서(33ms → 30ms) 30·15 FPS GIF가 약 10% 빨라졌고, 마지막 프레임이 10~19ms면 gifski가 그 시간을 받지 않았다. 이제 누적 시간을 0.01초로 반올림해 나눠 담고(30·40·30ms…), gifski와 같이 최소 20ms. 색 보호 GIF도 같은 규칙. 자동 테스트로 확인.
  - 참고: gifski는 20ms보다 짧은 프레임을 쓰지 않는다(늘린다). 그래서 예전에도 60 FPS GIF가 빨라지지는 않았고 오히려 약 1.2배 느려졌다.
- [x] 60 FPS 녹화의 GIF 저장: 녹화 기본값은 60 FPS 그대로 두고, GIF로 저장할 때 20ms보다 짧은 프레임이 있으면 "50 FPS로 맞춰 저장 / 그대로 저장 / 취소" 중 고른다. 50 FPS로 맞추기는 20ms 간격마다 그때 보이는 프레임을 골라(60 FPS면 6장 중 1장 빠짐) 이번 저장에만 적용하고 편집 중인 프레임은 그대로 둔다. 실제 앱에서 16ms × 15장을 저장해 50 FPS는 20ms × 12장(0.24초 유지), 그대로 저장은 20ms × 15장인 것을 확인.
- GIF 재생 시간 오류: 실제 녹화(편집 화면 7.3초)가 13.67초 GIF로 저장되는 것을 확인해 gifski의 마지막 프레임 시간 전달을 수정했다. 가변 시간과 단일 프레임 자동 테스트 통과. 수정 후 실제 앱에서 단일 프레임 4,407ms가 4,400ms로 저장된 것도 확인했다.
