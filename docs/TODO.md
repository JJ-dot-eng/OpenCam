Windows 빌드·테스트 확인은 아직): 깨진 동영상 불러오기 멈춤, 영상 저장 중 ffmpeg 출력 멈춤. 둘 다 ffmpeg의 오류 출력(stderr)을 끝난 뒤에야 읽어서, 64KB 넘게 쓰면 파이프가 차 서로 기다리며 멈췄다. 이제 ffmpeg를 켜자마자 다른 스레드에서 오류 출력을 끝까지 읽고 끝 8KB만 남겨 오류 메시지를 만든다(`export.rs`의 `spawn_stderr_tail`, 불러오기 `load_video`와 영상 저장 `video`가 같이 씀). 어느 길로 끝나든 stdin·stdout을 닫고 ffmpeg를 기다린 뒤 스레드를 join한다. MP4 바로 저장(`Mp4Stream`)은 오류 출력을 버리므로 그대로 둠. 확인한 것: Linux에서 따로 떼어서만 확인했다. 불러오기는 도우미 함수만 rustc 1.85로 따로 컴파일해 오류 출력이 약 130KB인 깨진 동영상에 돌려 보니 끝까지 가고 오류는 약 8KB만 남았다(옛 방식은 멈춤). 영상 저장도 같은 순서(프레임을 넣으면서 오류 출력을 따로 읽기)를 `export.rs`의 도우미 함수와 함께 rustc 1.85로 따로 떼어 만든 작은 프로그램과 ffmpeg로 확인했다: 오류 출력이 약 4MB일 때 옛 방식(`wait_with_output`)은 멈추고 새 방식은 끝까지 가고 끝 8KB만 남았다(Python으로도 같은 결과). 확인 못 한 것: 프로젝트 전체 컴파일, `cargo test`, rustfmt, Windows 실제 앱
- [x] 파일 끌어 놓기로 맨 뒤에 추가 (2026-10-31, 브랜치 feat/drag-drop-append, PR 아직 안 합침). 편집 중(프레임이 있을 때)에 파일을 끌어 놓으면 지금 프레임 맨 뒤에 붙인다. 프레임이 없으면 예전처럼 연다(동영상은 하나씩, 구간·옵션 창도 그대로). 정한 것: 순서는 폴더를 보지 않고 파일 이름만으로, 숫자는 크기대로(clip2 → clip10), 대소문자는 가리지 않고 이름이 같으면 전체 경로로(`src/fileOrder.ts`의 `compareFileNames`, "열기"의 여러 파일 순서도 이것으로 바꿈). 동영상 여러 개도 같은 순서로 붙인다. 크기는 지금 프레임에 맞추고 비율을 지키며 남는 곳은 투명(열기의 "비율 유지"와 같은 `fit_rgba` Contain). 동영상은 구간 창 없이 전체를, FPS는 설정 FPS와 원본 FPS 중 작은 쪽(동영상 열기 창의 처음 값과 같음), 크기는 지금 프레임 안에 맞춰 불러온 뒤 투명하게 채운다. 정지 이미지는 한 장에 100ms(이미지 열기 창의 처음 값). 편집 메모리 한도에서 이미 쓰는 만큼을 뺀 만큼만 더 불러오고(대략), 한도에 닿으면 그 파일은 앞쪽만 붙이고 알림, 뒤 파일은 건너뜀. 못 읽은 파일(지원하지 않는 형식, 깨진 파일, ffmpeg 없음 등)은 건너뛰고 나머지를 계속한 뒤 알림 창 하나로 이름과 까닭을 보여 준다. 모두 못 읽으면 아무것도 바뀌지 않는다. 한 번 놓은 것은 되돌리기 한 번(`Project::append`, Rust 명령 `append_files`)이고, 붙인 프레임이 선택된다. 처리 중이거나 창·도구 화면이 떠 있으면 단축키처럼 받지 않고 알림만 띄운다. 끌어 오는 동안 창 전체에 "놓으면 맨 뒤에 추가"(편집 중) 또는 "놓으면 열기" 표시. 확인한 것: `npx tsc --noEmit`, 파일 순서 테스트(`tests/file-order.test.mjs`, 이 PC는 Node 20이라 임시로 JS로 바꿔 돌림, 5개 통과). 확인 못 한 것: Rust 컴파일, `cargo test`(새 테스트: `append_is_one_undo_step`, 크기를 정해 불러오는 `load_files_sized` 확인을 기존 테스트에 더함), rustfmt, 실제 앱에서 끌어 놓기
- 나머지 새 기능은 당장 하지 않는다. 직접 써 보거나 사용자 반응을 보고 불편한 점을 모은 뒤 정한다. 자동 저장·복구와 다시 실행(Ctrl+Y)은 이미 했다(0.1.4). 남은 후보와 배치안은 [next-features.md](next-features.md)

### 1단계에서 남은 것 (녹화 틀)
- [x] 전체 화면 크기로 녹화: 현재 모니터 전체 좌표를 사용하고 녹화 틀을 캡처에서 제외한다. 실제 2560×1440 MP4를 저장해 화면 전체와 툴바 제외를 확인했다. 다른 모니터 배치·Windows 버전에서는 별도 확인 필요.
- [x] 녹화할 창 찾아 맞추기 (Ctrl+Shift+F 또는 녹화 틀 메뉴): 선택 시 현재 창 위치·크기를 다시 읽고 앞으로 가져온다. 실제 동영상 탐색기 창을 선택해 1439×893 녹화 및 GIF 저장 확인. 서로 다른 DPI의 다중 모니터는 추가 확인 필요.
- [x] 영역 드래그 선택 (Ctrl+Shift+D): 반투명 선택 창과 Esc 취소 구현. 실제 정·역방향 드래그 끝점과 Windows 커서 좌표 일치, 선택한 245×150 영역 녹화·GIF 저장과 Esc 취소 확인. 지연 응답과 취소가 동시에 발생하는 상황, 모니터 사이를 가로지르는 선택과 서로 다른 DPI는 실제 확인 필요.
  - 창 맞추기·영역 선택에서 툴바가 모니터 밖으로 나가면 반대쪽(위↔아래)으로 옮기고 설정 '툴바를 아래에'도 바꾼다. 화면 맨 위부터 드래그해 툴바가 아래로 옮겨지는 것을 실제 앱에서 확인. 위아래 모두 자리가 없으면(작업 표시줄 자동 숨김 + 최대화 창 등) 안내만 띄운다.
  - 모니터 배치의 빈 구석(크기가 다른 모니터 사이)에 걸친 선택은 이제 거절하고 "화면이 없는 부분이 있습니다"라고 알린다. 모니터들과 겹친 넓이의 합으로 검사(자동 테스트).
- [x] 이동·크기 조절 중 반투명 (설정 `useSemiTransparency`, 기본 켬): 툴바를 끌거나 가장자리를 잡으면 녹화 틀이 반투명해지고, 주 마우스 버튼(왼손잡이 설정 포함)을 떼면 돌아온다. 코드·타입 검사만 확인.
- [x] 이동·크기 조절 중 반투명의 실제 앱 동작 확인: 모서리를 누르고 있는 동안 반투명하고, 떼면 돌아오는 것을 확인 (2026-10-28). 툴바를 클릭만 할 때의 짧은 깜빡임은 직접 써 보며 판단할 것
- [x] 크기 조절 중 돋보기 (설정 `useMagnifier`, 기본 켬, `src-tauri/src/magnifier.rs`): 커서 주변을 3배로 보여 주는 둥근 렌즈(지름 240 CSS px). 커서 오른쪽 아래에 뜨고 작업 영역을 넘으면 반대쪽으로 간다. 커서 아래 픽셀은 빨간 네모로 표시. 주 마우스 버튼을 떼면 스스로 닫힌다. 화면 캡처에서 빠지게 해서 자기 자신을 확대하지 않는다. 실제 앱에서 모서리를 누르면 뜨고 떼면 닫히는 것, 렌즈 모양을 확인. 렌즈는 직접 그린다
- [x] Ctrl+PrtSc로 녹화 / 정지 (설정 `hotkeyCtrlPrtsc`, 기본 꺼짐): 녹화 단축키와 같으면 하나로 쓰고, 일시정지 단축키와 겹치면 알린다. 예전 설정 파일에서는 꺼진 채로 읽히는 것을 자동 테스트로 확인.

### 영상 짤(GIF·WebP) 측정 (2026-10-28)
짤은 대부분 영상으로 만들어서 문서 화면 대신 실제 게임 영상으로 쟀다. 원본: 직접 녹화한 게임 영상의 2~6초(풀숲 이동)를 480×480, 25 FPS, 100장으로 잘라 손실 없는 APNG로 묶었다. 위 24픽셀을 빼고 쟀다.
- [x] GIF 색 선택 개선: 기존 저장 결과는 SSIM 0.9883에서 약 19.5MB.
  - 원인: libimagequant가 픽셀마다 색을 고를 때 사람 눈 기준의 다른 색 공간을 쓰고 고른 뒤 팔레트를 또 다듬어서, 고른 번호의 13%가 실제로 가장 가까운 색이 아니었다.
  - 고침(`refine_nearest`): 화면 색(RGB)으로 가장 가까운 색을 다시 고르고, 팔레트 색을 그 색을 쓰는 픽셀들의 평균으로 옮기기를 3번 한다. 초록 값 순 탐색으로 빨라서 1080p 60장 저장 시간은 그대로(2.7초).
  - 결과(디더링 끔): 화질 80이 13.82MB·SSIM 0.9760·35.3dB → 13.53MB·0.9785·36.0dB. 화질 90은 17.97MB·SSIM 0.9891·39.5dB. 예전 그래픽 원본(mandelbrot)도 화질 80이 6.31MB·SSIM 0.914 → 6.32MB·0.944로 개선됐다. 5.2MB에서는 SSIM 0.919였다.
  - 디더링을 켜면 이 이득이 거의 사라진다(화질 80: 13.75MB·0.9758). 그래서 기본값을 끔으로 바꿨다(이미 저장된 설정 파일은 그대로). 하늘처럼 매끈한 곳을 확대해 봐도 끈 쪽에 띠가 보이지 않았다.
- [x] WebP: 약 3.24MB에서 SSIM 약 0.89, 화질 35에서 3.49MB·SSIM 0.906.
  - 아이폰 호환(모든 프레임 통째로, 기본 켬)이 오히려 낫다: 화질 60에서 크기 3% 늘고 PSNR 1.6dB 높다.
  - 알아 둘 것: `webp-animation` 0.10은 압축 방식(method) 값을 libwebp에 넘기지 않는다. 그래서 설정의 "압축 방식"은 지금 아무 효과가 없다(항상 4). ffmpeg로 재 보니 6은 5.6% 작지만 화질이 조금 낮고 18배 느려서(2초 → 36초) 고칠 가치는 낮다.

### 확인이 필요한 것
- [x] 녹화 중 "정지" 버튼을 한 번 눌렀는데 안 멈춘 적이 한 번 있다 (두 번째에 멈춤). 2026-10-27에 세 번, 2026-10-28에 다시 세 번(녹화 → 정지 한 번 클릭) 해 봤을 때 모두 한 번에 멈췄다. 처음 한 번은 테스트 도구가 초점을 옮긴 탓으로 본다. 정지 때 멈출 수 있던 잠금 문제(전역 Ctrl+S)는 따로 고쳤다.
- [x] GIF 프레임 시간: 예전에는 프레임마다 10ms 아래를 버려서(33ms → 30ms) 30·15 FPS GIF가 약 10% 빨라졌고, 마지막 프레임이 10~19ms면 gifski가 그 시간을 받지 않았다. 이제 누적 시간을 0.01초로 반올림해 나눠 담고(30·40·30ms…), gifski와 같이 최소 20ms. 색 보호 GIF도 같은 규칙. 자동 테스트로 확인.

- [x] 60 FPS 녹화의 GIF 저장: 녹화 기본값은 60 FPS 그대로 두고, GIF로 저장할 때 20ms보다 짧은 프레임이 있으면 "50 FPS로 맞춰 저장 / 그대로 저장 / 취소" 중 고른다. 50 FPS로 맞추기는 20ms 간격마다 그때 보이는 프레임을 골라(60 FPS면 6장 중 1장 빠짐) 이번 저장에만 적용하고 편집 중인 프레임은 그대로 둔다. 실제 앱에서 16ms × 15장을 저장해 50 FPS는 20ms × 12장(0.24초 유지), 그대로 저장은 20ms × 15장인 것을 확인.
- GIF 재생 시간 오류: 실제 녹화(편집 화면 7.3초)가 13.67초 GIF로 저장되는 것을 확인해 gifski의 마지막 프레임 시간 전달을 수정했다. 가변 시간과 단일 프레임 자동 테스트 통과. 수정 후 실제 앱에서 단일 프레임 4,407ms가 4,400ms로 저장된 것도 확인했다.
