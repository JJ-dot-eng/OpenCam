## 이번 작업: 진행률 99% 정체 (2026-11-02, Codex, PR #18)

- 재현 자료: 저장소 밖 Linux 재현 결과(ffmpeg 7.1). 입력 `-ss`·`-t`, `fps,scale`, RGBA 파이프를 쓰는 앱 명령을 `/usr/bin/ffmpeg`로 그대로 비교했다. 회귀 테스트의 영상 생성 명령(32×24, 10fps, 1초 장면이 6초까지 머묾)도 다시 실행했다. 정상 영상뿐 아니라 긴 정지 프레임, 길이 정보 없는 영상, 전체 붙이기, 0이 아닌 구간 시작을 확인했다. 실행 기록은 저장소 밖에 있다.
- 고치기 전 Windows CI 실패: run 41436704112에서 `video_range_ending_inside_held_frame_keeps_frame_count`가 60장(6000ms), `raw_video_progress_reaches_full_after_eof`가 진행률 `[0.333,0.667,0.99]`로 실패했다. 이미 커밋된 두 테스트를 포함해 기존 테스트는 바꾸지 않았다.
- RESULTS.md의 실제 수치: `vfr_hold_mid.mp4` 150장 예상에 400장, `hold_last.mkv`·`nodur_hold_mid.webm` 450장 예상에 1200장, `hold_last.mp4` 303장 예상에 1200장. 출력의 63~75%가 99%에 머물렀다. 720p 정지 영상은 최대 메모리 1258MB, 긴 정지 WebM은 3GB 상한에서 300장 뒤 메모리 부족으로 실패했다. ffmpeg 종료 대기는 1ms 미만이라 오래 걸리는 원인이 아니었다.
- 고친 것: `import.rs`에서 원래 입력 `-ss`·`-t`를 두고 `fps` 바로 뒤에 `trim=end_frame=N`을 넣었다. N은 기존 진행률의 예상 장수(구간 길이 × FPS를 올림)다. 초과 복제 프레임이 크기 변환·출력 쪽에 쌓이지 않게 한다. 출력 `-t` 후보도 비교했지만 `vfr_hold_mid.mp4`의 12~15초 구간에서 기존 30장이 0장이 되어 고르지 않았다. 선택한 trim 방식은 이 구간도 30장을 유지했다.
- 진행률: `collect_raw_frames`가 한 장 이상을 읽고 정상 EOF에 도달하면 마지막에 1.0을 한 번 보낸다. 그 전 값은 0.99 이하이며, 부분 프레임·읽기 오류·메모리 한도에서는 1.0을 보내지 않는다. `append_files`는 파일별 진행률을 0.99 이하로 두고, 모든 파일을 경고·건너뜀·메모리 한도 없이 읽어 현재 프로젝트에 붙인 뒤에만 1.0을 한 번 보낸다. 이미지 한 장의 0%, 동영상 한 개의 99% 종료도 처리했다. 작업 변경·붙이기 실패에는 완료를 보내지 않는다.
- 직접 확인한 장수(고치기 전 → 후): 회귀 영상 0~2초 60 → 20장(6000 → 2000ms), `hold_last.mkv` 1200 → 450장, `hold_last.mp4` 전체 붙이기 1200 → 303장, `vfr_hold_mid.mp4` 400 → 150장, `nodur_hold_mid.webm` 1200 → 450장, `cfr30.mp4` 450 → 450장. 길이 없는 WebM은 앱과 같은 스트림 복사 탐색으로 길이 45.966초를 확인한 뒤 전체 붙이기 1379 → 1379장, CFR 전체 붙이기 600 → 600장, CFR 5~7.25초 68 → 68장도 확인했다. 모든 수정 후 명령은 정상 종료했고 부분 프레임 바이트는 없었다.
- 메모리 확인: ffmpeg 주소 공간에 3,000,000KiB 상한을 건 상태로만 실행했다. 이번 환경에서 `vfr_hold_mid_720.mp4`는 기존 100장 뒤 실패(종료 244) → 150장 정상, 최대 RSS 1184.6 → 368.8MiB. `nodur_hold_long_720.webm`은 기존 300장 뒤 실패(종료 244) → 450장 정상, 최대 RSS 1136.1 → 700.6MiB. RESULTS.md와 상한 단위·실행 조건이 달라 기존 720p 출력 장수는 다를 수 있다.
- 새 Rust 단위 테스트 1개: `raw_video_incomplete_read_never_reports_full`(부분 프레임·읽기 오류·메모리 한도 세 경우에 1.0을 보내지 않는지 확인). Rust 타입·빌림·콜백 시그니처와 기존 부분 읽기 경고 경로를 코드로 검토했다. `finish_video`·길이 탐색·붙이기 여백과 메모리 계산은 바꾸지 않았다.
- Node 확인: PATH 앞에 `~/.local/opt/node22/bin`을 넣고 Node 22.23.4에서 `npm ci`, `npx tsc --noEmit` 통과. 지정한 `node --experimental-strip-types --test tests/*.test.mjs`도 통과했으나 이 환경의 출력은 파일 7개로 집계됐다. 개별 테스트 수를 확인하려고 `node --experimental-strip-types --experimental-test-isolation=none --test tests/*.test.mjs`를 추가 실행해 55개 통과·실패 0·건너뜀 0을 확인했다. 기존 테스트 파일은 수정하지 않았다. `git diff --check` 통과.
- 확인 못 한 것: 이 PC에서는 Rust 빌드·cargo 실행을 하지 않았다. 수정 후 두 회귀 테스트와 새 단위 테스트의 실행은 Windows CI에서 확인해야 한다. Windows PC의 실제 앱(불러오기·동영상/이미지 붙이기·부분 읽기 경고·메모리 한도), 함께 쓰는 ffmpeg.exe, 늦게 도착한 `import-progress` 이벤트가 다음 작업 글자를 덮는지도 확인하지 못했다.
- 남은 문제: `audio_longer.mp4`처럼 컨테이너가 영상보다 길면 예상 장수가 커서 읽는 동안 60~80%까지만 오르는 반대 방향 문제는 그대로다(이번 비교도 360 → 360장). 정상 EOF에는 이제 마지막 1.0을 보내지만 길이 추정 자체는 고치지 않았다. 커밋·push·브랜치 조작·버전 변경은 하지 않았다.

- [x] 파일 끌어 놓기로 맨 뒤에 추가 (2026-10-31, 브랜치 feat/drag-drop-append, PR 아직 안 합침). 편집 중(프레임이 있을 때)에 파일을 끌어 놓으면 지금 프레임 맨 뒤에 붙인다. 프레임이 없으면 예전처럼 연다(동영상은 하나씩, 구간·옵션 창도 그대로). 정한 것: 순서는 폴더를 보지 않고 파일 이름만으로, 숫자는 크기대로(clip2 → clip10), 대소문자는 가리지 않고 이름이 같으면 전체 경로로(`src/fileOrder.ts`의 `compareFileNames`, "열기"의 여러 파일 순서도 이것으로 바꿈). 동영상 여러 개도 같은 순서로 붙인다. 크기는 지금 프레임에 맞추고 비율을 지키며 남는 곳은 투명(열기의 "비율 유지"와 같은 `fit_rgba` Contain). 동영상은 구간 창 없이 전체를, FPS는 설정 FPS와 원본 FPS 중 작은 쪽(동영상 열기 창의 처음 값과 같음), 크기는 지금 프레임 안에 맞춰 불러온 뒤 투명하게 채운다. 정지 이미지는 한 장에 100ms(이미지 열기 창의 처음 값). 편집 메모리 한도에서 이미 쓰는 만큼을 뺀 만큼만 더 불러오고(대략), 한도에 닿으면 그 파일은 앞쪽만 붙이고 알림, 뒤 파일은 건너뜀. 못 읽은 파일(지원하지 않는 형식, 깨진 파일, ffmpeg 없음 등)은 건너뛰고 나머지를 계속한 뒤 알림 창 하나로 이름과 까닭을 보여 준다. 모두 못 읽으면 아무것도 바뀌지 않는다. 한 번 놓은 것은 되돌리기 한 번(`Project::append`, Rust 명령 `append_files`)이고, 붙인 프레임이 선택된다. 처리 중이거나 창·도구 화면이 떠 있으면 단축키처럼 받지 않고 알림만 띄운다. 끌어 오는 동안 창 전체에 "놓으면 맨 뒤에 추가"(편집 중) 또는 "놓으면 열기" 표시. 확인한 것: `npx tsc --noEmit`, 파일 순서 테스트(`tests/file-order.test.mjs`, 이 PC는 Node 20이라 임시로 JS로 바꿔 돌림, 5개 통과). 확인 못 한 것: Rust 컴파일, `cargo test`(새 테스트: `append_is_one_undo_step`, 크기를 정해 불러오는 `load_files_sized` 확인을 기존 테스트에 더함), rustfmt, 실제 앱에서 끌어 놓기
- [x] 저장 오류 2개 고침 (2026-10-31, 브랜치 fix/save-errors-png-sequence): GIF 저장이 마지막 종료 표시 쓰기와 버퍼 비우기 오류를 버려 실패해도 "저장함"으로 보이던 것을 고침(인코더를 직접 마무리하고 비운 뒤 오류를 돌려줌). ### 영상 짤(GIF·WebP) 측정 (2026-10-28)
짤은 대부분 영상으로 만들어서 문서 화면 대신 실제 게임 영상으로 쟀다. 원본: 직접 녹화한 게임 영상의 2~6초(풀숲 이동)를 480×480, 25 FPS, 100장으로 잘라 손실 없는 APNG로 묶었다. 위 24픽셀을 빼고 쟀다.
- [x] GIF 색 선택 개선: 기존 저장 결과는 SSIM 0.9883에서 약 19.5MB.
  - 원인: libimagequant가 픽셀마다 색을 고를 때 사람 눈 기준의 다른 색 공간을 쓰고 고른 뒤 팔레트를 또 다듬어서, 고른 번호의 13%가 실제로 가장 가까운 색이 아니었다.
  - 고침(`refine_nearest`): 화면 색(RGB)으로 가장 가까운 색을 다시 고르고, 팔레트 색을 그 색을 쓰는 픽셀들의 평균으로 옮기기를 3번 한다. 초록 값 순 탐색으로 빨라서 1080p 60장 저장 시간은 그대로(2.7초).
  - 결과(디더링 끔): 화질 80이 13.82MB·SSIM 0.9760·35.3dB → 13.53MB·0.9785·36.0dB. 화질 90은 17.97MB·SSIM 0.9891·39.5dB. 예전 그래픽 원본(mandelbrot)도 화질 80이 6.31MB·SSIM 0.914 → 6.32MB·0.944로 개선됐다. 5.2MB에서는 SSIM 0.919였다.
  - 디더링을 켜면 이 이득이 거의 사라진다(화질 80: 13.75MB·0.9758). 그래서 기본값을 끔으로 바꿨다(이미 저장된 설정 파일은 그대로). 하늘처럼 매끈한 곳을 확대해 봐도 끈 쪽에 띠가 보이지 않았다.
- [x] WebP: 약 3.24MB에서 SSIM 약 0.89, 화질 35에서 3.49MB·SSIM 0.906.
  - 아이폰 호환(모든 프레임 통째로, 기본 켬)이 오히려 낫다: 화질 60에서 크기 3% 늘고 PSNR 1.6dB 높다.
  - 알아 둘 것: `webp-animation` 0.10은 압축 방식(method) 값을 libwebp에 넘기지 않는다. 그래서 설정의 "압축 방식"은 지금 아무 효과가 없다(항상 4). ffmpeg로 재 보니 6은 5.6% 작지만 화질이 조금 낮고 18배 느려서(2초 → 36초) 고칠 가치는 낮다.

### 확인이 필요한 것
- [x] 녹화 중 "정지" 버튼을 한 번 눌렀는데 안 멈춘 적이 한 번 있다 (두 번째에 멈춤). 2026-10-27에 세 번, 2026-10-28에 다시 세 번(녹화 → 정지 한 번 클릭) 해 봤을 때 모두 한 번에 멈췄다. 처음 한 번은 테스트 도구가 초점을 옮긴 탓으로 본다. 정지 때 멈출 수 있던 잠금 문제(전역 Ctrl+S)는 따로 고쳤다.
- [x] GIF 프레임 시간: 예전에는 프레임마다 10ms 아래를 버려서(33ms → 30ms) 30·15 FPS GIF가 약 10% 빨라졌고, 마지막 프레임이 10~19ms면 gifski가 그 시간을 받지 않았다. 이제 누적 시간을 0.01초로 반올림해 나눠 담고(30·40·30ms…), gifski와 같이 최소 20ms. 색 보호 GIF도 같은 규칙. 자동 테스트로 확인.
  - 참고: gifski는 20ms보다 짧은 프레임을 쓰지 않는다(늘린다). 그래서 예전에도 60 FPS GIF가 빨라지지는 않았고 오히려 약 1.2배 느려졌다.
- [x] 60 FPS 녹화의 GIF 저장: 녹화 기본값은 60 FPS 그대로 두고, GIF로 저장할 때 20ms보다 짧은 프레임이 있으면 "50 FPS로 맞춰 저장 / 그대로 저장 / 취소" 중 고른다. 50 FPS로 맞추기는 20ms 간격마다 그때 보이는 프레임을 골라(60 FPS면 6장 중 1장 빠짐) 이번 저장에만 적용하고 편집 중인 프레임은 그대로 둔다. 실제 앱에서 16ms × 15장을 저장해 50 FPS는 20ms × 12장(0.24초 유지), 그대로 저장은 20ms × 15장인 것을 확인.
- GIF 재생 시간 오류: 실제 녹화(편집 화면 7.3초)가 13.67초 GIF로 저장되는 것을 확인해 gifski의 마지막 프레임 시간 전달을 수정했다. 가변 시간과 단일 프레임 자동 테스트 통과. 수정 후 실제 앱에서 단일 프레임 4,407ms가 4,400ms로 저장된 것도 확인했다.
